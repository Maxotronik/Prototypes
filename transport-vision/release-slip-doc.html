01 · Background
The Problem

When a carrier arrives at a pickup location to collect a vehicle, the lot attendant needs to release it. Today this handoff is informal — carriers rely on phone calls, printed paperwork, or verbal confirmation to establish that they have the right job. There's no standardized digital document that a carrier can present at the gate.

The Release Slip is a generated document that formalizes this handoff: a scannable, shareable record that identifies the carrier, the vehicle, and the job — enough for the releasing party to confirm and sign off.

02 · Goals
What We're Trying to Achieve
1
Give carriers a single digital document to present at pickup — eliminating the need for printed paperwork or phone calls to confirm identity and authorization.
2
Make the slip easy to share via the carrier's preferred channel — email or SMS — at the moment it's needed, with minimal steps.
3
Explore the interaction patterns (modal vs. context menu) for surfacing the Release Slip action from within the Manage page job list.
03 · Document Content
What the Release Slip Contains

The Release Slip is generated from the job data already in the system — no additional carrier input is required. The document surfaces the information that the releasing party needs to verify the handoff.

SectionFields
Vehicle identityYear / Make / Model, VIN, color, odometer reading (if available)
Job referenceOrder ID, job type (open / enclosed / drive my car)
Carrier infoCarrier name, MC number, driver name
Pickup detailsPickup address, scheduled pickup date, lot contact
Delivery detailsDelivery address, scheduled delivery date
AuthorizationACV authorization reference, QR code or confirmation code for verification
In the prototype, document content is populated from the job data array. Fields that are not available for a given job are omitted rather than shown as empty.
04 · Delivery Patterns
How Carriers Access & Share the Slip
Entry point — from the Manage page

The Release Slip action is available on dispatched and picked-up jobs in the Manage page. It is hidden when the Action Required filter is active, as that mode is focused on exception handling, not standard job actions.

Two interaction patterns are prototyped and can be toggled via the ProtoUI FAB:

open_in_new Pattern A — Modal (default)
  • Tapping the Release Slip button on any eligible job opens the full slip in a modal overlay.
  • Desktop: 480px centered modal. Mobile: full-screen overlay with a sticky bottom action bar.
  • Desktop modal footer: Email and SMS buttons side by side (both rs-footer-desktop class).
  • Mobile: a single "Share" button opens the native OS share sheet with Email and SMS pre-populated as options.
more_vert Pattern B — Context Menu
  • Tapping the Release Slip button opens a position:fixed context menu with four items: Download / View / Email / SMS.
  • Desktop: a popover positioned above or below the button based on available viewport space.
  • Mobile: a bottom sheet with the same four items as a stacked list.
  • Email and SMS are direct actions — no intermediate Share sub-popover.
  • Email calls emailRS(); SMS calls shareSMS().
Sharing channels

Both patterns support Email and SMS as the two sharing channels. No WhatsApp or Telegram — the design intentionally limits to the two channels most universally available in a professional context. The recipient (typically the lot or auction) receives a link or PDF attachment depending on the channel.

05 · Platform Behavior
Technical & UX Behaviors
Feature Announcements — disabled on load

The Release Slip prototype is based on manage-page.html, with the Feature Announcements system disabled at initialization. All MODAL_STEPS are marked as read and tooltipFired is set to true on page load — the What's New button remains functional, but no modal or tooltip fires automatically.

This keeps the Release Slip prototype focused on the slip interaction itself, without the announcement overlay interfering during testing or presentation.

Body scroll lock

When the Release Slip modal opens, body receives position: fixed. This prevents iOS Safari's scroll-through behavior, where momentum scrolling on a fixed overlay still scrolls the underlying page.

ProtoUI mode switching

The ProtoUI FAB switches all job cards simultaneously between Modal and Context Menu mode. It calls setRSMode(mode), which sets useContextMenu on each job object and triggers renderManageList() to rebuild the card list. The FAB is hidden on GitHub Pages (via the ProtoUI env detection snippet) and shows as icon-only on mobile (≤ 900px).

06 · Decision Log
Key Design Decisions
DecisionRationale
Email + SMS only (no WhatsApp / Telegram) Lot attendants and dispatchers operate in a professional context where email and SMS are universal. Messaging app availability varies and adds complexity without a clear benefit for this use case.
Mobile Share = OS native sheet The native iOS/Android share sheet surfaces all apps the user has installed — email, SMS, and others — without requiring ACV to maintain a list of supported apps. It's also familiar and faster than a custom share UI.
Feature Announcements disabled in this prototype The Release Slip prototype exists as a focused exploration of the slip interaction. Keeping it isolated from the announcement system makes it easier to test and present without side effects.
Prototype split from manage-page.html into its own file The Release Slip has enough distinct behavior (both action patterns, different announcement state) to warrant its own file rather than a mode toggle inside the Manage page. Splitting also allows version control per prototype independently.
Context menu: no sub-popover for Share Adding a Share sub-menu (which would then list Email and SMS) is one step too many. Email and SMS are already the final actions — the context menu should be the last step before acting, not an intermediate navigation point.
