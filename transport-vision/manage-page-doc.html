01 · Overview
What This Prototype Is

The Manage page is the carrier's active job management surface — the place where staged and in-progress jobs live. It is distinct from the Job List (browsing/discovery) in that users arrive here with clear, task-oriented goals: take action on jobs that require it, monitor the status of jobs in progress, and dispatch or follow up on deliveries.

The prototype explores the information architecture, filter system, view modes, and integrated flows (Release Slip, Feature Announcements) that make the Manage page an effective operational tool for both desktop dispatchers and mobile-first carriers.

Two primary users
desktop_windows Dispatcher (desktop)
  • Manages multiple drivers and trucks from a fixed workstation.
  • Needs an overview of all active and staged jobs with enough density to plan the day.
  • Relies on filters and sort controls to prioritize work across a large job pool.
phone_iphone Independent carrier (mobile)
  • Drives and manages their own business from a phone.
  • Needs quick access to the jobs that require immediate action — not a full list to manage.
  • Bottom navigation and mobile-first layout prioritize speed over density.
02 · Header & Navigation
Chrome & Navigation
Desktop header
  • ACV logo (links to index) → tab bar (Job List / Staged / Manage active) → What's New button → user avatar + name/company → hamburger menu.
  • Tabs are the primary navigation between the three loadboard surfaces. Manage is the active tab in this prototype.
Mobile header (≤ 768px)
  • Hamburger (left) → "ACV Transport Load Board" centered → search icon (right).
  • Logo, tabs, and user info are hidden on mobile — replaced by a bottom navigation bar.
  • Bottom nav: Job List / Stage / Manage (active, orange accent). Fixed at the bottom of the viewport.
The desktop-first tab bar and the mobile bottom nav are two representations of the same navigation model. They share the same three destinations but are optimized for their respective contexts.
03 · Filter Bar
Filtering & Sorting
Desktop layout

The filter bar is split into two rows. Row 1 contains density-requiring controls: search box, Status chip (STATUS: ACTIVE dropdown), Pickup Location, Delivery Location, Job Type, and Sort By chip (default: Priority). Row 2 contains toggle chips and the mobile Filters button.

Toggle chips (row 2)
warning Action Required
  • Filters the job list to show only jobs with active alerts: pickup-past-due, pickup-today, delivery-past-due, deliver-today, or no-BOL.
  • When active, the Release Slip action is hidden from all job cards to keep the surface focused on exception handling.
  • Activating Action Required deactivates Schedule View if it was on.
calendar_view_week Schedule View
  • Groups jobs into collapsible time-based sections: Today / Tomorrow / Later.
  • Each group header is fully clickable (collapse/expand) — child elements have pointer-events disabled to prevent accidental interactions while scrolling.
  • Groups with no jobs are hidden entirely.
  • Activating Schedule View deactivates Action Required if it was on.
Action Required and Schedule View are mutually exclusive. Both answer a different version of the same question — "what should I look at now?" — but from opposite angles: one filters by urgency, the other by time. Showing both simultaneously would create ambiguous groupings.
Mobile filter

On mobile, a "Filters" button (margin-left: auto, placed right-aligned in row 2) replaces the full desktop filter row. It opens a sheet or modal with the same controls condensed for touch.

05 · Views & Modes
Schedule View & Action Required
Schedule View — grouping logic

When Schedule View is active, the job list is reorganized into three collapsible time sections based on pickup or delivery date relative to today:

  • Today — jobs with a pickup or delivery scheduled for the current date.
  • Tomorrow — jobs scheduled for the next calendar day.
  • Later — all remaining jobs beyond tomorrow.

Group headers are fully interactive — clicking anywhere on the header expands or collapses the section. Child job cards have pointer-events: none applied to the header click zone to prevent accidental card interactions during header taps on touch devices.

Action Required — filter behavior

When Action Required is active, only jobs matching one or more of the five alert types are shown. The Release Slip button is removed from all visible cards — the filter signals intent to handle exceptions, and presenting non-exception actions adds distraction.

06 · Release Slip
Generating & Sharing the Release Slip

The Release Slip is a digital transport handoff document generated from a staged or dispatched job. It contains vehicle details, pickup/delivery instructions, and carrier contact info — enough for the receiving party to confirm identity and release the vehicle.

Two action patterns (prototype only)
open_in_new Modal (default)
  • All dispatched and picked-up jobs open the full Release Slip modal directly.
  • Desktop: 480px centered overlay. Mobile: full-screen with a bottom action bar.
  • Modal footer (desktop): Email and SMS side by side. Mobile: single Share button that opens the native OS share sheet.
menu Context Menu
  • Dispatched and picked-up jobs open a position:fixed context menu with four items: Download / View / Email / SMS.
  • Desktop: positioned as a popover anchored to the button, above or below based on viewport space.
  • Mobile: opens as a bottom sheet with the same four items as a list.
  • No intermediate Share sub-popover — Email and SMS are direct actions.
Mode switching (ProtoUI)

A ProtoUI FAB (bottom-left, 80px from bottom) lets the designer switch all job cards between Modal and Context Menu mode simultaneously. It calls setRSMode(mode), which sets useContextMenu on each job and re-renders the list. The FAB is hidden on GitHub Pages and icon-only on mobile.

07 · Feature Announcements
In-Page Announcement System

The Manage page includes a self-contained Feature Announcements system (IIFE) that demonstrates how new features and changes are communicated to carriers. It is a scoped subset of the full system prototyped in feature-announcements.html.

What's in the prototype
  • Two announcements in the HISTORY array; no intro announcement.
  • Announcement 1 (filters-update, May 28 2026, modal channel): "Status filters are now part of the main filter bar." Includes a chained tooltip with two steps — Step 1 anchored to the Action Required chip, Step 2 to the Schedule View chip.
  • Announcement 2: a placeholder for a second announcement.
  • Modal fires 700ms after page load. Closing it triggers the chained tooltip once (tooltipFired flag prevents repeat within the session).
What's New panel
  • Lists all HISTORY entries. Each chainedTooltip step appears as a separate item in the panel (with a tips_and_updates icon).
  • Clicking a tooltip item in the panel fires that single step directly — without opening the modal.
  • Opening the announcement detail modal from the panel also fires the chain (if not yet fired) when it closes.
See Feature Announcements documentation for the full system spec including all delivery channels, segmentation rules, and journey maps.
08 · Decision Log
Key Design Decisions
DecisionRationale
Action Required hides Release Slip When filtering for exceptions, showing non-exception actions adds cognitive noise. The filter communicates intent — the UI responds to it.
Action Required and Schedule View are mutually exclusive Both answer "what do I look at now?" from different angles — urgency vs. time. Combining them would create ambiguous groupings (is a today-due job in "Today" or "Action Required"?).
Mobile bottom nav instead of header tabs Tabs in a sticky header on mobile require a stretch gesture to reach. Bottom nav puts the three primary surfaces within thumb range — the pattern matches how mobile-first carriers actually use the app.
Schedule View group headers: full-row click, children pointer-events none On touch, a small header target causes mis-taps on the child cards. Making the full row the click target fixes this. Disabling pointer-events on children within the header zone ensures the collapse/expand action always wins.
Release Slip modal: body position:fixed on open Prevents iOS scroll-through — a known Safari bug where fixed overlays still allow the underlying page to scroll via momentum.
v3 is current; v1 and v2 preserved as history Each version represents a meaningfully different direction. Keeping them allows comparison and rollback reference without polluting the main file.
